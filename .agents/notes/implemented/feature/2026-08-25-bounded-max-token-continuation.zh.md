# Agent Note: 有界自动续写负责输出上限恢复

Status: implemented

[English](2026-08-25-bounded-max-token-continuation.md) | 中文

## Problem

提供方可能在只输出回答前缀后，以 `max-tokens` 正常结束。会话会保留该前缀，Web 客户端也会标明截断，但恢复过程要求用户手动发送“继续”。提高模型的输出 token 设置只能降低出现频率，无法消除这一失败模式；如果网关反复执行更小的上限，无界自动重试还可能无限消耗提供方调用。

## Decision

`@deepseek-ai/dsh-max-token-continuation` 是由 base bundle（基础组合包）安装的独立 guard 策略。在 `agent/turn-stopping` 阶段，它检查当前轮最后一次提供方结束原因。若为 `max-tokens`，它会把一条已记录的插件通知引导到同一轮的下一步骤；其他结束原因不触发任何操作。该指令要求模型从截断处继续、不重复已完成内容，并在不完整工具调用因截断被丢弃时重新发出完整调用。

该策略默认每轮最多自动续写三次。`maxContinuations: 0` 会关闭自动续写；加载期校验会拒绝负数、小数上限和空白指令。每个 agent 的计数存放在 `WeakMap` 中，并按轮次标识重置。此状态有意不持久化：活动轮次及其进程拥有重试执行。

agent loop 使用最后一次尝试的步骤决定轮次结果。因此续写成功会产生 `completed`；如果最后一次允许的尝试仍达到上限，该轮保留 `max-tokens`，现有持久警告会告知用户仍可手动继续。每次被截断的提供方调用仍有自己的 `assistant/message` 锚点，因此所有已输出前缀和注入指令都可从会话日志重建。

## Alternatives considered

**只提高每个模型的 `maxTokens`。** 这是有用的配置，但无法保证完成：网关可能执行更低上限，模型输出长度会变化，而更长的单次回答仍有有限上限。

**不设置重试上限。** 不采用，因为始终返回 `max-tokens` 的提供方会造成无界同轮循环和无界成本。

**把续写直接内置到 agent loop。** 不采用，因为自动重试次数和指令文本属于部署策略。loop 负责步骤时序和最终结果语义；guard 插件负责是否请求另一步骤。

**成功续写后仍让 `max-tokens` 保持粘滞。** 不采用，因为回答已经完成后，客户端仍会显示截断警告。单次调用被截断仍是持久事实；轮次结果描述最终尚未解决的状态。

## Consequences

普通 base bundle 会话无需用户操作即可从最多三次连续输出上限截断中恢复。恢复成功会移除手动继续警告，次数耗尽则保留该警告。续写会增加模型调用和保留的提示文本；由于运行时不拼接生成文本，模型可能重复少量交界内容。[max-tokens 提示决策](../bug-fix/2026-08-12-max-tokens-turn-end-notice.zh.md)仍负责次数耗尽后的呈现，[回放状态对齐决策](../bug-fix/2026-08-15-max-token-replay-state-alignment.zh.md)继续负责安全重建被截断的工具调用回答；二者都没有被完全取代。

自动续写依赖压力压缩为下一步骤腾出空间。因此，辅助摘要调用会直接应用已路由提供方的重试策略：可重试的终止型传输失败会在解析出的延迟后启动新的摘要流；取消、重试耗尽与不可重试失败仍遵循现有压缩失败行为。这避免了瞬时摘要连接失败在上下文未变化且已满时消耗续写次数。
